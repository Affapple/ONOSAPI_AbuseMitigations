# 4.2 Lab Setup

This section describes the experimental infrastructure used in the SDN API-abuse project, including the network topology, ONOS deployment, authentication mechanisms, and multi-tenant isolation model.

## 4.2.1 Mininet Topology Configuration

### Network Structure

The experimental network is a small, fixed topology built with Mininet and OpenFlow 1.3, implemented in `/Project/topology/tenants.py`. The topology consists of three OpenFlow switches and four hosts organized as follows:

- **Switches**: Three switches (s1, s2, s3) with fixed OpenFlow device IDs:
  - s1 (dpid=0x0000000000000001): Core/backbone switch
  - s2 (dpid=0x0000000000000002): Edge switch for tenant t1 and t2 hosts
  - s3 (dpid=0x0000000000000003): Edge switch for tenant t1 and t2 hosts

- **Topology Diagram**:
  ```
                    s1 (shared core)
                   /                \
                s2                    s3
             /      \              /      \
          h1a        h2a        h1b        h2b
  ```

- **Links** (trunk ports connecting the backbone):
  - s1 port 1 ↔ s2 port 3
  - s1 port 2 ↔ s3 port 3

### Multi-Tenancy Model

The topology implements multi-tenancy through subnet isolation and policy enforcement, not through address space separation:

**Tenant t1** (`10.0.1.0/24`):
- Hosts: h1a (10.0.1.1, MAC `00:00:00:00:01:01`), h1b (10.0.1.2, MAC `00:00:00:00:01:02`)
- Edge ports: s2/1, s3/1
- Accounts: t1-op (operator), t1-view (viewer)

**Tenant t2** (`10.0.2.0/24`):
- Hosts: h2a (10.0.2.1, MAC `00:00:00:00:02:01`), h2b (10.0.2.2, MAC `00:00:00:00:02:02`)
- Edge ports: s2/2, s3/2
- Accounts: t2-op (operator), t2-view (viewer)

**Global configuration**:
- All hosts are configured with `/16` prefix length (instead of `/24`) to allow ARP to work across tenants at the L2 level; tenant isolation is enforced through policy, not L3 routing
- Port numbers are fixed in the Mininet topology definition so that connect points in `tenants.json` remain stable
- IPv6 is disabled on all hosts to reduce control-plane chatter
- The service account `gw-svc` (for the gateway's read-only proxy) is configured globally

### Topology Instantiation

Topology management is controlled by `/Project/topology/mnctl.sh`, which provides non-interactive commands:

- `mnctl.sh start [--static-arp]`: Builds the network using `tenants.py run`, running detached as a daemon with PID file
- `mnctl.sh stop`: Terminates the topology via SIGTERM
- `mnctl.sh status`: Displays daemon PID, host PIDs (from `/proc`), IP/MAC assignments, and OVS controller connection state
- `mnctl.sh exec <host> <cmd>`: Executes a command inside a Mininet host namespace
- `mnctl.sh discover [timeout]`: Initiates host learning by triggering ARP requests and verifies the ONOS view against `tenants.json`
- `mnctl.sh clean`: Removes stale OVS bridges and state files

Topology state is maintained in `/tmp/sdn-tenants/state.json` and `/tmp/sdn-tenants/tenants.pid`, with logging to `/tmp/sdn-tenants.log`.

## 4.2.2 ONOS Deployment

### ONOS Container and Configuration

ONOS runs in a Docker container (`onos`) with the following configuration:

- **Base version**: Apache Karaf 4.2.14
- **Controller connection**: Defaults to `127.0.0.1:6653` (OpenFlow 1.3)
- **REST API endpoint**: `http://localhost:8181`
- **Configuration directory**: `/root/onos/apache-karaf-4.2.14/etc`

### User Authentication (Karaf JAAS)

User credentials are stored in `users.properties` and authenticated by Karaf's PropertiesLoginModule, which re-reads the file on every login (no restart required for changes to take effect). Three overlays exist:

1. **Stock configuration** (`users.stock.properties`):
   - Default ONOS users: `karaf:karaf`, `onos:rocks`
   - Default guest account: `guest:guest` with viewer role
   - Used to restore the container to a baseline state

2. **Configuration C1 (No Controls)** (`users.noctl.properties`):
   - Tenant accounts (t1-op, t1-view, t2-op, t2-view) are placed in the **admingroup**, granting them full access to `/onos/v1`
   - `gw-svc` is in guestgroup (viewer only)
   - Gateway is unused; all modules are disabled
   - Represents the case where tenants bypass the gateway and access ONOS directly

3. **Configuration C2/C3 (Tenant-based)** (`users.tenant.properties`):
   - Tenant accounts (t1-op, t1-view, t2-op, t2-view) are placed in a custom **tenantgroup**, granting them only the "tenant" role
   - This role has no `/onos/v1` access; all requests must go through the gateway
   - `gw-svc` is in guestgroup (viewer only) for the gateway's read-only proxy operations
   - Gateway is active and enforces module-specific access control

**Karaf Roles and Groups** (defined in users.properties):
- `admingroup`: admin, manager, viewer, systembundles, ssh, webconsole
- `guestgroup`: viewer
- `tenantgroup`: tenant (custom role for gateway-enforced access)

### Applied Overlay and Module State

The overlay is applied via `/Project/karaf/apply.sh`:
- **Syntax**: `karaf/apply.sh [--no-restart] <overlay>` where overlay is `stock`, `noctl`, or `tenant`
- **Default behavior**: Copies the overlay file to the container, restarts ONOS, waits for readiness, verifies rediscovery
- **--no-restart flag**: Skips the restart and rediscovery check for rapid configuration changes (uses re-login to apply)
- **Account probe**: After overlay application, the script verifies that tenant credentials produce expected HTTP status codes:
  - C1 (noctl): t1-op → 200, guest → 401
  - C2/C3 (tenant): t1-op → 403, guest → 401
  - Stock: onos → 200, guest → 200

### Installed Applications

The following ONOS applications are relevant to the evaluation:

- `lu.uni.sdn.api_gateway` (gateway app): Activated based on configuration; implements all security modules (B1–B6)
- `lu.uni.sdn.southbound_mac_extractor` (MacCollector): Extracts MAC addresses from packet-ins to assist host learning
- `org.onosproject.fwd` (Simple Forwarding): May be active but is flagged as polluting measurements
- `org.onosproject.proxyarp` (Proxy ARP): Handles ARP replies for host learning

## 4.2.3 Tenant Roles and Access Control

### Role Definitions

Tenant access is controlled through a three-tier role model defined by the gateway's `GatewayRole` enum:

#### Viewer
- **Karaf role(s)**: "viewer" (from tenants.json account definition)
- **Gateway role**: VIEWER
- **Permissions**:
  - GET requests on `/onos/gw/v1/*` endpoints (proxied to `/onos/v1/*` with the read-only service account credentials)
  - Cannot write flows, intents, or other configuration
  - Can query device, link, host, and flow state
  - Throttling (B6) applies to rejections but cannot trigger write-side effects

#### Operator
- **Karaf role(s)**: "tenant" (custom role in C2/C3 configurations)
- **Gateway role**: OPERATOR
- **Permissions**:
  - POST/DELETE requests on `/onos/gw/flows` and `/onos/gw/intents` to manage rules
  - GET requests on `/onos/gw/v1/*` (read access)
  - Full access to flows/intents owned by their tenant
  - Subject to all gateway checks (B1–B6): ACL, Rate limit, Quota, Validation, Conflict, Throttle

#### Admin
- **Karaf role(s)**: "admin" (must be both in Karaf's admin role AND listed in tenants.json "admins" array)
- **Gateway role**: ADMIN
- **Permissions**:
  - Unrestricted access to all gateway endpoints (admin-only paths under `/onos/gw/admin`)
  - POST/PUT/DELETE on `/onos/gw/v1/*` proxied with their own authorization header (not the service account)
  - Can reset throttle state via `/gw/admin/tenants/{id}/unblock`
  - Bypass all tenant-specific checks but are still subject to logging/audit

#### Service Account
- **Karaf role(s)**: "viewer" (in guestgroup)
- **Gateway role**: SERVICE
- **Permissions**:
  - Used internally by the gateway for GET requests to `/onos/v1/*` on behalf of tenant callers
  - Credentials: `gw-svc:gw-svc-pw` (from tenants.json "serviceAccount" field)
  - Cannot make write requests; failures cannot propagate as writes
  - Used when a tenant makes a GET request on the proxy (`/onos/gw/v1/*`)

### Authentication and Identity Resolution

Authentication is a two-stage process:

1. **Stage 1: Karaf JAAS Login**
   - HTTP Basic Auth credentials are authenticated against the Karaf user database (users.properties)
   - If authentication fails, the request returns HTTP 401 Unauthorized
   - Karaf roles are determined by the user's group membership in users.properties

2. **Stage 2: Gateway Identity Resolution** (`CallerIdentity.resolve`)
   - The `GatewayFilter` servlet filter extracts the Karaf principal and probes the security context for Karaf roles
   - The gateway consults `tenants.json` to determine:
     - If the user is a tenant account (tenant ID and account role: "operator" or "viewer")
     - If the user is listed in the "admins" array → potential ADMIN role
   - **Gateway role assignment**:
     - If listed in "admins" AND has the Karaf "admin" role → ADMIN
     - Else if a tenant account with "operator" role → OPERATOR
     - Else if a tenant account with "viewer" role → VIEWER
     - Else if the user is the "serviceAccount" → SERVICE
     - Else → NONE (authenticated but unknown to the gateway; requests fail with 500)

The calleridentity is attached to the request context and consulted by all gateway resources.

## 4.2.4 Multi-Tenant Isolation and Environment

### Tenant Isolation Mechanisms

The gateway implements isolation through multiple independent mechanisms:

#### 1. Ownership-Based ACL (B1)
- Defined in `acl/Ownership.java` and enforced by `acl/AppIdImposer.java`
- Every flow/intent is tagged with the tenant's ApplicationId (assigned by the gateway, not the caller)
- Requests are validated to ensure they only reference ports, hosts, and rules owned by the tenant's subnet
- Violation → HTTP 403 Forbidden (reason: spoofed_source, foreign_destination)

#### 2. ACL Path Control (B1)
- Defined in `acl/PathAcl.java` and enforced before each resource method
- Different endpoints have different access rules:
  - `/onos/gw/flows` and `/onos/gw/intents`: Operators can write; viewers read-only
  - `/onos/gw/v1/*`: Proxied to ONOS; access controlled by `aclEnabled` toggle
    - If `aclEnabled=false` (C1, reconnaissance setting): Viewers can read all tenants' rules
    - If `aclEnabled=true` (C2, C3): Viewers can only read their own tenant's rules
  - `/onos/gw/admin/*`: Admin-only endpoints

#### 3. Per-Tenant Rate Limiting (B2)
- Implemented by `ratelimit/TokenBucketLimiter.java`
- Each tenant maintains a token bucket with capacity 20 tokens and a refill rate of 10 tokens/second (default: `rateLimitRps=10.0`, `rateLimitBurst=20`)
- Every request consumes one token; requests without tokens are rejected with HTTP 429 Too Many Requests
- Rejection reason: "rate_limit"

#### 4. Per-Tenant Quotas (B3)
- Implemented by `quota/QuotaManager.java`
- Per-tenant limits (from `tenants.json` or defaults):
  - `maxFlowsPerTenant`: 100 (default)
  - `maxFlowsPerTenantPerDevice`: 40 (default)
  - `maxIntentsPerTenant`: 20 (default)
  - `churnLimit`: 200 (default: adds + deletes per 60-second window)
- Quota violations return HTTP 409 Conflict (for capacity limits) or HTTP 429 Too Many Requests (for churn; with Retry-After header)

#### 5. Payload Validation (B4)
- Implemented by `validation/PayloadValidator.java`
- Validates individual flow/intent rules:
  - Priority must be within range [minPriority=100, maxPriority=30000]
  - Rule must have an expiration (timeout must be > 0 and ≤ maxTimeout=300 seconds)
  - Rule cannot be a catch-all (must match at least one criterion beyond in-port and type)
  - Rule cannot send traffic to the controller (action type cannot be OUTPUT:CONTROLLER)
- Violation → HTTP 400 Bad Request (reason: validation_<specific-failure>)

#### 6. Cross-Tenant Conflict Detection (B5)
- Implemented by `conflict/ConflictDetector.java`
- Detects rules that would interfere with other tenants:
  - **Spoofed source**: Matching a source IP/MAC not belonging to the calling tenant
  - **Destination capture**: Matching a destination IP/MAC belonging to another tenant
  - **Overlap conflict**: Matching traffic in another tenant's subnet with higher priority
- Violation → HTTP 409 Conflict (reason: spoofed_source, dst_capture, or overlap_conflict)

#### 7. Adaptive Throttling (B6)
- Implemented by `throttle/ThrottleManager.java`
- Tracks per-tenant rejection scores based on rejections from B1–B5
- Rejection weights: ACL (3.0), Rate Limit (1.0), Validation (3.0), Conflict (5.0), Quota (2.0)
- Escalation levels:
  - Level 0 (score < threshold1=10): No effect
  - Level 1 (10 ≤ score < 25): Rate factor = 0.5 (tenant gets half the normal request budget)
  - Level 2 (25 ≤ score < 50): Rate factor = 0.5 (same as Level 1)
  - Level 3 (score ≥ 50): Write operations blocked (HTTP 429)
- Cooldown: Once score drops below level threshold, tenant remains cooldown-restricted for 30–960 seconds
- Modes:
  - **Adaptive** (default, C3): Score-based escalation
  - **Fixed** (C3F): Fixed penalty of 60 seconds when any rejection occurs (Lab2-like behavior)

### Multi-Tenant Authentication

Each tenant has two accounts in Karaf (`users.properties`):
- `{tenant}-op` (password `{tenant}-op-pw`): Operator role (can write)
- `{tenant}-view` (password `{tenant}-view-pw`): Viewer role (read-only)

Example for t1:
- `t1-op = t1-op-pw,_g_:tenantgroup` (C2/C3) or `_g_:admingroup` (C1)
- `t1-view = t1-view-pw,_g_:tenantgroup` (C2/C3) or `_g_:admingroup` (C1)

Authentication flow for a tenant operator request:
1. Client sends HTTP Basic Auth with `t1-op:t1-op-pw`
2. Karaf JAAS verifies credentials against `users.properties`
3. `CallerIdentity.resolve()` determines: user=t1-op, tenant=t1, gatewayRole=OPERATOR (C2/C3) or ADMIN (C1)
4. Gateway enforces role-specific access control

### Configuration Scenarios

Three experimental configurations are defined in `/Project/harness/onosctl.py`:

| Config | ONOS Overlay | Gateway API Target | Modules Enabled | Use Case |
|--------|-------------|-------------------|-----------------|----------|
| **C1** | noctl | `/onos/v1` | None (all off) | Baseline: tenant bypasses gateway, direct ONOS access |
| **C2** | tenant | `/onos/gw` | ACL only (B1) | ACL enforcement without performance cost |
| **C3** | tenant | `/onos/gw` | All (B1–B6) | Full protection with all checks |
| **C3F** | tenant | `/onos/gw` | All (B1–B6, fixed throttle) | Full protection with fixed penalty (Lab2 comparison) |

Configuration is applied via `/Project/harness/config.sh`:
```
harness/config.sh <C1|C2|C3|C3F> [--no-restart] [--out FILE]
```

This script:
1. Applies the Karaf overlay and optionally restarts ONOS
2. Waits for the gateway app to be ACTIVE
3. Purges all intents and non-core flows
4. Sets all gateway properties (via `/onos/v1/configuration/lu.uni.sdn.apigateway.GatewayManager`)
5. Unblocks tenants (resets throttle state)
6. Triggers topology rediscovery to synchronize ONOS

## 4.2.5 Gateway REST API Endpoints

The gateway exposes the following REST API endpoints under `/onos/gw`:

### Tenant-Facing Endpoints

| Method | Path | Role | Description |
|--------|------|------|-------------|
| **GET** | `/gw/flows[?tenant=]` | Viewer, Operator | List flows owned by the caller's tenant (or admin-specified tenant) |
| **POST** | `/gw/flows[?tenant=]` | Operator | Install flows; body: `{"flows":[...]}` (ONOS format) |
| **DELETE** | `/gw/flows[?tenant=]` | Operator | Remove flows; body: `{"flows":[{"deviceId":..,"flowId":..}]}` |
| **DELETE** | `/gw/flows/{deviceId}/{flowId}` | Operator | Remove a single flow |
| **GET** | `/gw/intents[?tenant=]` | Viewer, Operator | List intents owned by the caller's tenant |
| **POST** | `/gw/intents[?tenant=]` | Operator | Install intents; body: ONOS intent JSON |
| **DELETE** | `/gw/intents[?tenant=]` | Operator | Remove intents; body: `{"intents":[...]}` |
| **DELETE** | `/gw/intents/{intentKey}` | Operator | Remove a single intent |
| **GET** | `/gw/v1/{path}` | Viewer, Operator | Proxy to `/onos/v1/{path}` with service account; filtered to tenant's hosts/flows/intents (if `aclEnabled=true`) |
| **POST** | `/gw/v1/{path}` | Admin | Proxy POST to `/onos/v1/{path}` with caller's credentials |
| **PUT** | `/gw/v1/{path}` | Admin | Proxy PUT to `/onos/v1/{path}` with caller's credentials |
| **DELETE** | `/gw/v1/{path}` | Admin | Proxy DELETE to `/onos/v1/{path}` with caller's credentials |

### Admin-Only Endpoints

| Method | Path | Description |
|--------|------|-------------|
| **GET** | `/gw/admin/tenants` | List all tenants' quota usage, throttle status, and conflict counts |
| **GET** | `/gw/admin/tenants/{id}` | Quota usage, throttle state, and conflict info for a specific tenant |
| **POST** | `/gw/admin/tenants/{id}/unblock` | Reset tenant's throttle score, level, cooldown, and fixed penalty |
| **GET** | `/gw/whoami` | Return caller's identity: user, roles, tenant, gatewayRole, appId |

### Error Handling

All rejections return JSON responses with two fields:
- `reason`: Machine-readable rejection code (e.g., "acl", "rate_limit", "quota_flows", "validation_priority")
- `message`: Human-readable detail

HTTP status codes and reason codes:
- **400 Bad Request**: validation_* reasons (payload validation failure)
- **401 Unauthorized**: Invalid credentials (Karaf JAAS)
- **403 Forbidden**: acl, unknown_account, tenant_mismatch reasons; tenant blocked (B6, level 3)
- **404 Not Found**: not_found (endpoint or resource does not exist)
- **409 Conflict**: quota_flows, quota_flows_device, spoofed_source, dst_capture, overlap_conflict (payload conflict)
- **429 Too Many Requests**: rate_limit, quota_churn, throttle_paused reasons (with optional Retry-After header)
- **500 Internal Server Error**: no_identity, internal error (request did not pass through GatewayFilter)
- **502 Bad Gateway**: upstream_error (upstream ONOS returned 401/403 or other error)
