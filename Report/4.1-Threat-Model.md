# 4.1 Threat Model & Attack Scenarios

## Overview of Authorized Tenant Abuse in Multi-Tenant ONOS

In a multi-tenant Software-Defined Networking (SDN) environment with ONOS, authenticated tenants are granted access to a subset of the network via profile-based Access Control Lists (ACLs). An "operator" role (such as `t1-op`) typically receives permissions to:

- **POST to flow endpoints** – to install and modify OpenFlow flow rules on switches
- **POST to intent endpoints** – to submit high-level intents (e.g., HostToHostIntent, PointToPointIntent)
- **DELETE flow/intent resources** – to remove rules and intents
- **GET topology, devices, links, flows, intents, hosts** – to query network state

Access control, however, is binary: a request is either allowed or denied based on identity and endpoint. It does not restrict:
- **Request rate or frequency** – how many requests an operator makes per second or minute
- **Request size or complexity** – how large a payload is or how many items it contains
- **Resource impact** – how much controller CPU, memory, or switch flow-table space is consumed
- **Payload semantics** – whether a flow rule makes logical sense or conflicts with network policy

An authenticated tenant operating within their assigned permissions can therefore exploit these gaps. By abusing legitimate API endpoints, a tenant can:

1. **Exhaust controller resources** – overload the controller with read and write operations
2. **Degrade latency for other tenants** – fill queues and monopolize processor time
3. **Fill switch flow tables** – install high-churn rules that consume precious hardware resources
4. **Interfere with other tenants' traffic** – install capture, drop, or rewrite rules that target traffic from or to other tenants' hosts
5. **Trigger semantic errors or unexpected behavior** – submit malformed or conflicting flow/intent definitions

This section describes the four abuse scenarios evaluated in this project.

## Scenario S1: API Flooding and Resource Exhaustion

### Attack Description

Scenario S1 combines **flow rule installation/deletion cycles** with **repeated read queries** to exhaust controller resources.

**Implementation (s1_flood.py):**
- Tenant `t1-op` logs in with valid credentials
- Every 10 iterations:
  - Posts a **batch of 10 flow rules** to the same switch (S2) with varying priorities
  - Immediately calls **drain_flows()** to delete all created flows
- Between batches, makes sequential **GET requests** to:
  - `/flows` (all flows)
  - `/intents` (all intents)
  - `/devices` (all devices)
  - `/links` (all links)
  - `/topology` (topology)
  - `/hosts` (all hosts)
- Repeats this cycle for a configurable duration (e.g., 60 seconds)
- Respects an optional rate limit (e.g., 0 requests/second = unlimited)

**Legitimate permissions used:**
- `POST /flows` – operator is authorized to install flows
- `DELETE /flows` – operator is authorized to remove flows
- `GET /flows`, `/intents`, `/devices`, `/links`, `/topology`, `/hosts` – operator can query network state

### Impact on Controller

1. **CPU saturation** – the controller processes JSON parsing, flow compilation, flow-table lookups, and state queries continuously
2. **Memory pressure** – internal flow rule cache, intent compiler state, and accumulated network topology data compete for heap
3. **API response latency** – legitimate tenant queries are queued behind flood requests, increasing wait time
4. **Flow-table thrashing** – the switch experiences rapid churn of rules (create, delete, create, delete), consuming TCAM wear and triggering OpenFlow transaction overhead

### Attack Success Criteria

- Controller CPU utilization > 80%
- POST/GET latency for other tenants increases by 2–10×
- Legitimate flow-rule installation by other tenants is delayed

## Scenario S2: Flow-Rule Churn

### Attack Description

Scenario S2 focuses on **high-velocity flow-rule churn** – the creation and near-immediate deletion of flow rules – to maximize switch resource consumption and OpenFlow transaction overhead.

**Implementation (s2_churn.py):**
- Tenant `t1-op` performs a continuous attack loop:
  - Posts a **batch of 20 flow rules** to switch S2 with sequential priorities starting at 10000
  - Upon successful POST (HTTP 200–299):
    - **Immediately calls drain_flows()** to delete all 20 rules
  - Requests are issued at a configurable rate (default: 0 = unlimited)
- Each rule is a simple match-on-port(1)-and-eth-type, action output-to-port(3) with a 60-second timeout
- Churn continues for the entire attack duration

**Legitimate permissions used:**
- `POST /flows` – install batches of flow rules
- `DELETE /flows` – delete batches or individual flow rules

### Impact on Controller

1. **Controller state churn** – the internal flow cache is constantly updated and invalidated
2. **Switch overhead** – each create and delete command is sent to the switch via OpenFlow, consuming switch CPU and transaction buffers
3. **Memory fragmentation** – rapid allocation and deallocation of rule objects may trigger garbage collection storms
4. **Southbound bottleneck** – OpenFlow connections to switches are saturated with modify commands, reducing bandwidth for legitimate network operations

### Attack Success Criteria

- Legitimate flow-rule installation latency increases significantly (100–300 ms observed)
- Switch reports flow-table modification errors due to transaction queue overflow
- OpenFlow connection utilization approaches 100%

## Scenario S3: Semantic Flow Abuse

### Attack Description

Scenario S3 tests **semantically invalid or policy-violating flow rules and intents**. Rather than raw flooding, it focuses on the submission of rules that exploit weaknesses in the controller's validation layer.

**Implementation (s3_semantic.py):**
- Tenant `t1-op` cycles through nine different attack variants (selected via `--variant` flag):

| Variant | Type | Payload | Purpose | Impact |
|---------|------|---------|---------|--------|
| **catchall** | Flow | No match criteria, output to port 2 | Matches all packets on S1 | Intercepts all traffic crossing S1 |
| **dropall** | Flow | No match criteria, drop action | Silently discards all packets on S2 | Blanket denial of service |
| **permanent** | Flow | Simple match, permanent timeout flag | Rule never expires | Consumes switch memory indefinitely |
| **foreign_port** | Flow | Match on port 2 of S2 | Attempts to match on port not assigned to this tenant | May violate port ACLs |
| **controller** | Flow | Match criteria, OUTPUT to CONTROLLER | Redirects traffic to controller | Floods controller with packet-in messages |
| **p2p_empty** | Intent | P2P intent with empty criteria | Intent with no match specification | Undefined behavior in intent compiler |
| **constraints** | Intent | HostToHost intent with bandwidth constraint (1000 Mbps) | Resource claim on paths between hosts | May exhaust bandwidth quota or cause scheduling failures |
| **missing_prereq** | Flow | IPv4_SRC match without ETH_TYPE | Match criteria with unfulfilled dependency | Validation failure or unexpected behavior |
| **catchall_top** | Flow | No criteria, priority 40001 (highest), 1-second timeout | Extreme-priority catch-all | Overrides all other rules due to high priority |

- Each variant is posted once per cycle, then deleted if successful
- Attack cycles through all variants at a configurable rate (default: 4 requests/second)
- Runs for a configurable duration (default: 60 seconds)

**Legitimate permissions used:**
- `POST /flows`, `POST /intents` – operator can install flows and intents
- `DELETE /flows`, `DELETE /intents` – operator can remove them
- Operators are **not explicitly restricted** from using match criteria or actions that the controller should validate

### Impact on Controller

1. **Validation bypass** – if the controller lacks strong semantic validation, invalid flows may be accepted and installed
2. **Priority inversion** – high-priority catch-all rules can override lower-priority legitimate rules
3. **Controller-directed attacks** – sending traffic to the CONTROLLER port can saturate the controller's packet-in queue
4. **Resource exhaustion via constraints** – intent constraints may cause the path compiler to consume excessive CPU searching for feasible paths
5. **Unpredictable behavior** – malformed intents and rules may cause parsing errors, state inconsistencies, or crashes

### Attack Success Criteria

- Invalid flows are accepted and installed (HTTP 201 instead of 400)
- Catch-all rules suppress legitimate traffic
- Intent compiler reports errors or hangs
- Packet-in rate to the controller spikes

## Scenario S4: Intent-Based Cross-Tenant Interference

### Attack Description

Scenario S4 tests **cross-tenant traffic manipulation** – the use of flow rules and intents to intercept, modify, or redirect traffic belonging to other tenants.

**Implementation (s4_cross_tenant.py):**
- Tenant `t1-op` cycles through eight attack variants, each targeting traffic from or to tenant 2 (T2) hosts:

| Variant | Type | Payload | Target | Attack Method |
|---------|------|---------|--------|----------------|
| **dst_capture** | Flow | Match destination MAC = H2B_MAC (T2 host), output port 1 | T2 host H2B | Broad L2 capture: any packet destined to T2:H2B is diverted |
| **dst_capture_owned** | Flow | Narrow match (ingress port + ETH_TYPE + src=H1A + dst=H2B), output port 2 | T2 host H2B from T1:H1A | More specific capture: only traffic from T1:H1A to T2:H2B is diverted |
| **spoof_src** | Flow | Match ingress port 1, rewrite source MAC to H2A_MAC (T2 host), output port 3 | T2 traffic source | Spoof outbound traffic with T2's MAC address |
| **rewrite_dst** | Flow | Match src=H1A, rewrite dst MAC to H2B, output to port 3 | T2 host H2B | Redirect T1's outbound traffic to T2's host |
| **capture_ip** | Flow | Match destination IP subnet 10.0.2.0/24 (T2's subnet), output to port 3 | T2 subnet | L3 capture of all traffic destined to T2's network |
| **intent_cross** | Intent | HostToHostIntent between H1A (T1) and H2B (T2) | T2 host H2B | Intent spanning tenant boundaries – may cause path conflicts |
| **p2p_capture** | Intent | P2P Intent from (S2, port 1) to (S3, port 1), matched on (src=H1A, dst=H2B) | T2 traffic | Specific point-to-point path for T2 traffic |
| **p2p_spoof** | Intent | P2P Intent with src MAC spoofed to H2A (T2 host) | T2 source identity | Intent claiming T2's identity |

- Each variant is held for 2 seconds (allowing propagation and traffic diversion) then deleted
- Attack cycles through all variants at a configurable rate (default: 0.4 requests/second)

**Legitimate permissions used:**
- `POST /flows`, `POST /intents` – operator can install flows and intents (there is no per-tenant validation of which hosts they may target)
- `DELETE /flows`, `DELETE /intents` – cleanup after attack
- The controller's ACL typically does not restrict **what traffic** a flow rule or intent targets – it only decides whether the operator **can submit requests**

### Impact on Other Tenants

1. **Traffic interception** – T2's traffic is diverted to T1-controlled ports or to the controller
2. **Packet header rewriting** – T2 packets have their source or destination MAC/IP modified, breaking end-to-end connectivity
3. **Intent path conflicts** – cross-tenant intents may cause the path compiler to install conflicting rules
4. **Network partitioning** – capture rules can isolate T2 hosts from reaching their destinations
5. **Service disruption** – T2 tenants experience packet loss, redirects, or spoofed sources

### Attack Success Criteria

- T2 traffic is successfully redirected (can be observed via packet capture on diverted ports)
- T2 hosts lose connectivity to each other or to external networks
- Cross-tenant intents are accepted and alter the forwarding path
- T2's legitimate flows are deprioritized by T1's high-priority capture rules

## Summary Table

| Scenario | Attack Type | Legitimate Permission | Resource Targeted | Tenant Impact |
|----------|-------------|----------------------|-------------------|--------------|
| **S1** | Read + write flooding | POST/DELETE flows, GET all state | Controller CPU, memory, API queue | Latency degradation for all tenants |
| **S2** | Flow-rule churn | POST/DELETE flows in batches | Switch flow-table, OpenFlow channel | Latency spike on flow installation |
| **S3** | Semantic violations | POST flows/intents (unrestricted payload) | Controller validation logic, intent compiler | Unexpected behavior, priority inversion, DoS via packet-in |
| **S4** | Cross-tenant interference | POST flows/intents (no host-level ACL) | Other tenants' traffic, host connectivity | Traffic interception, packet modification, isolation |

All scenarios demonstrate that **ACL-based access control is necessary but insufficient** to prevent abuse. An authenticated tenant granted legitimate permissions can exhaust resources, degrade service, and interfere with other tenants. Additional defenses (rate limiting, quotas, semantic validation, conflict detection) are required to complement ACLs.

## Threat Model Assumptions

This threat model assumes:

1. **Tenant credentials are not compromised** – we do not defend against stolen passwords; ACL enforcement is assumed to work correctly
2. **OpenFlow dataplane is trusted** – we do not defend against rogue switches or southbound protocol attacks
3. **Tenants operate at the same privilege level** – there is no "super-tenant" exception; all operators have equivalent access
4. **The controller is non-Byzantine** – the controller enforces its own policies correctly and does not collude with attackers
5. **Network topology is static** – we do not consider dynamic link failures or switch additions/removals during the attack
6. **Intent resolution is deterministic** – path conflicts are resolved according to documented (not adversarial) rules

## Scope Limitations

The following threat vectors are **explicitly out of scope**:

- Southbound attacks against the OpenFlow protocol or malicious switches
- Compromise of the ONOS admin or service accounts
- Attacks on the ONOS web GUI or other non-API interfaces
- Cluster-level attacks (split-brain, poisoned cluster state)
- Denial of service via large packet-in floods that overwhelm the dataplane entirely (not API-induced)
- Timing attacks or side-channel analysis of the controller
